# PostgreSQL migration

MongoDB Atlas (Flex/Serverless) bills for every document and index key that is read or written (see `docs/database-performance.md`). PR #24 reduced how often we hit the database, but the pricing model itself remains the cost driver. We are moving to a self-hosted PostgreSQL, accessed through Drizzle ORM.

The migration is done in phases on the `migration/postgres-drizzle` branch, which was created from `main` after PR #24. Each phase is reviewed before the next one starts. The older branches `feat/postgreSQL-migration` (Prisma) and `feature/postgessql` are **not** used as a base. The Prisma branch is consulted only to cross-check fields and the edge cases its data-copy script handles.

## Decisions

| Topic | Decision | Why |
|---|---|---|
| ORM / driver | Drizzle ORM with `pg` (node-postgres); migrations through `drizzle-kit` | SQL-first, small client, works on serverless, and has typed JSONB support |
| Postgres hosting | Self-hosted VPS running Postgres 17, with PgBouncer in transaction mode in front | Predictable flat cost |
| App hosting | Stays on Vercel, including Vercel Cron | Needs PgBouncer, and Vercel functions pinned to the same region as the VPS |
| Region | The VPS goes in Singapore. Vercel is pinned to `sin1` **at cutover**, not before | Vercel runs in its default region (`iad1`) today, alongside Atlas. Moving it before cutover could slow every Mongo query |
| Primary keys | `char(24)` columns holding the existing ObjectId hex strings; new ids are generated by the app with `bson`'s `ObjectId` | Ids already appear in URLs, JWTs, the IndexedDB offline store and about 58 client files. Keeping them avoids remapping ids during the data copy |
| API response shape | The DB column is `id`; the repository layer returns `_id` and the same nested shapes `populate()` produced | Client code does not change in this migration |
| Data modeling | Hybrid. Data that is queried or updated atomically becomes child tables. Data that is read as a whole becomes JSONB | Stock updates and line items need row-level atomicity. `Tenant.settings` is read as one blob |
| Tenant isolation | Enforced in the app: every repository method requires `tenantId`. Cross-tenant leak tests back this up. No row-level security | Avoids wrapping every query in a transaction. Keeps today's rule that every query is scoped to a tenant |
| Code rollout | A repository layer (`lib/db/`), migrated one domain at a time behind a `DB_DRIVER=mongo\|postgres` flag | Each step can be merged and tested on its own, and rollback is a single flag |
| Cutover | One short maintenance window: freeze writes, copy the data, verify it, flip `DB_DRIVER` | Simplest approach, with no risk of the two databases drifting apart |

## Sizing (Phase 0)

```bash
pnpm db:size-report                         # per-collection counts and sizes, estimated child-table rows
pnpm db:size-report -- --by-tenant --top=20 # adds the largest tenants (more Atlas reads)
```

The script is read-only. Run it against production, or a restored snapshot, with a read-only user. It writes `db-size-report.json`, which is gitignored. Its numbers determine the batch size for the data copy and the expected length of the maintenance window.

## Mongo behavior that needs a Postgres replacement

| Mongo | Postgres |
|---|---|
| TTL indexes on OfflineTransaction, SavedCart, CustomerOTP, FeatureFlagOverride, PosSession and RevokedToken | `lib/automations/ttl-cleanup.ts` cron job doing batched `DELETE`s |
| Partial unique indexes | Partial unique indexes (`WHERE ... IS NOT NULL`); `NULLS NOT DISTINCT` for z-readings |
| Booking overlap check in a pre-save hook | Exclusion constraint on `tstzrange` (`btree_gist`) |
| Delete guards in hooks (Product, Category, Discount, SubscriptionPlan) | `ON DELETE RESTRICT` foreign keys, or explicit checks |
| Cache-invalidation hooks (`lib/cache.ts`) | Explicit calls in the repository write methods, after commit |
| `$regex` search (28 places) / `$text` (prescriptions) | `ILIKE` with `pg_trgm` GIN indexes / a `tsvector` column |
| `Counter` with `$inc` + upsert (`lib/receipt.ts`) | `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` |
| `runWithOptionalMongoTransaction` / `startSession` | `runInTransaction` (`lib/db/tx.ts`) |
| Duplicate-key error `11000` | `DuplicateKeyError` (`lib/db/errors.ts`), which also covers Postgres error `23505` |
| `$merge` archiving, `*_archive` collections | `INSERT INTO ..._archive SELECT ...; DELETE ...` in one transaction |
| JSON backup/restore scripts | `pg_dump` / pgBackRest |

## Schema conventions (Phase 2)

- **Ids** are `char(24)` ObjectId hex strings (`db/schema/_columns.ts`). The data copy keeps each Mongo `_id` exactly; new rows get `new ObjectId()`.
- **Every tenant-scoped table** has `tenant_id NOT NULL` with a foreign key to `tenants`, and **no** `ON DELETE CASCADE`. Deleting a tenant stays an explicit operation.
- **Child tables** (items, variations, branch stock, billing history and the like) carry `tenant_id`, `position` (the original array order) and `ON DELETE CASCADE` from their parent.
- **References:** a required reference blocks deletion of the row it points to (`RESTRICT`). An optional reference uses `SET NULL`. Polymorphic ids (`audit_logs.entity_id`, `super_admin_actions.target_id`) are plain text with no foreign key.
- **Enum fields** are `text` plus a CHECK constraint, not Postgres `ENUM` types, so adding a value is a one-line migration. The allowed values are exported as `UPPER_SNAKE` constants.
- **Number types:** money is `numeric(14,2)`, quantities and stock are `numeric(14,3)`, and rates are `numeric(12,6)`. All are returned as JS numbers.
- **JSONB** is used for data that's read as a whole: `tenants.settings`, product modifiers, `customers.addresses`, invoice customer snapshots, payment details, audit `changes`/`metadata`, the POS session cart, and the plan feature flags.
- **Mongoose behaviour the schema can't express** moves to the repository layer in Phase 3. Each table has a comment listing what moves. It includes:
  - trimming and lowercasing values
  - hashing passwords with bcrypt
  - Booking's `end_time` and `staff_name`
  - Attendance's `total_hours`
  - the conditional negative-stock check
  - delete guards that depend on a status
  - cache invalidation
  - applying Mongoose defaults inside JSONB

## Existing-data findings (handle in the data copy, Phase 5)

- **Product variations are probably broken in production today.** In Product, ProductBundle, ProductChannelListing and StockMovement, `variation(s): { size, color, type: String }` is read by Mongoose as "this path is a String", because `type` is Mongoose's type-declaration key. Mongoose then rejects variation objects. Tested: `Cast to [string] failed`. The Postgres schema uses the intended `{size, color, type}` shape. The data copy must check what is actually stored: likely empty arrays, or strings.
- **Defaults become NOT NULL.** Many fields that Mongoose gave defaults are `NOT NULL DEFAULT …` in Postgres. Older documents missing them get the default during the copy.
- **Old documents may break the new CHECK constraints** (email format, non-negative amounts, percentages ≤ 100). Mongoose only validates on `save()`, not on most updates, so the copy must report and fix these rows.
- **New uniqueness rules:** `product_branch_stock` allows one row per (product, branch), and the booking constraint rejects overlapping bookings. Existing duplicates and overlaps must be found before loading.

## Rules to keep as they are (do not change them during the migration)

- `User.email` is unique across all tenants.
- `Table.name` is unique per tenant, not per branch.
- `StockMovement` identifies a variation by its size, color and type values, not by id.
- `isActive` treats a missing value as true (`TENANT_IS_ACTIVE_FILTER`). The data copy sets an explicit default for these documents.

## Cutover runbook (Phase 8)

1. Announce the window to tenants. POS devices keep working offline, and queued transactions sync afterwards with their original ids.
2. Turn maintenance mode on with the `MAINTENANCE_MODE` flag in `proxy.ts`, which makes write APIs return 503. Pause Vercel cron.
3. Take a final Mongo backup: `pnpm db:backup:cloud`.
4. Run the data copy, then the verification. Decide go or no-go against the thresholds recorded during the Phase 7 rehearsals.
5. Set `DB_DRIVER=postgres` and `DATABASE_URL`. Pin Vercel functions to the VPS region with `"regions": ["sin1"]` in `vercel.json`. Redeploy, run the smoke tests, turn maintenance mode off, and resume cron.
6. **Rollback.** Within the decision window (for example 1 hour), set `DB_DRIVER` back to `mongo`. Atlas stays untouched and read-only during this period. After the window, fix problems forward.
